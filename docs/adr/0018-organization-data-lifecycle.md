# ADR 0018: Organization data lifecycle — export and anonymization

- Status: Accepted
- Date: 2026-08-19

## Context

A production-readiness audit found this the single largest disclosed gap in the repository: no privacy inventory, minimization, retention, deletion, or export path existed anywhere (README's own Priority 1 list; independently confirmed by a market-readiness assessment built the same day). Before real customer data can responsibly be held, a customer must have a real way to get their data out and a real way to ask for it to stop existing.

This intersects directly with ADR 0003's design: most provenance-bearing tables (`source_records`, `leads`, `invoices`, `tasks`, `signals`, `recommendations`, `audit_events`) are deliberately append-only for ordinary application access — "ordinary application roles may select and insert... but may not update or delete them... only narrow lifecycle fields may change through a future audited retention path." This ADR is that path, scoped narrowly to what a real request requires.

## Decision

**Export, not deletion, for the read side.** `exportOrganizationData` (`packages/persistence/src/organization-lifecycle.ts`) gathers every real record an organization has — leads, invoices, tasks, Daily Brief artifacts, recent audit events, subscription state — into one structured object. Every read reuses or extends existing, already-tested query functions (`listAllLeads`/`listAllInvoices`/`listAllTasks`, capped at 1000 each and disclosed as such; `listRecentAuditEvents`'s existing 10-item cap, also disclosed rather than presented as a full historical dump). No new table, no new role — this is ordinary `SELECT` access the app already has.

**Anonymization, not deletion, for the write side.** `anonymizeOrganization` scrubs personally-identifying fields (`organizations.display_name`, the sole-membership user's `display_name`/`primary_email`, `leads.contact_name`/`company_name`, `invoices.customer_name`, `tasks.assignee_name`) and marks the organization `deactivated_at`. It does **not** delete rows, and does not touch `source_records`, `signals`, `recommendations`, or `audit_events` — those retain real provenance/audit value, and a hard delete of `organizations` would fail outright regardless (`audit_events.organization_id` restrict-references `organizations`, by design, so nothing referencing it can cascade away silently). This was a deliberate choice over row deletion: Postgres's own restrict-heavy FK chain (confirmed by inspection — `leads`/`invoices`/`tasks` restrict-reference `source_records`, `signals` restrict-references `leads`, `recommendations` restrict-references `signals`) made a clean cascading delete impossible without first weakening constraints ADR 0003 put there on purpose, and doing so would have traded away real audit value for a delete that Postgres would refuse anyway on any organization with real history.

**`organizations.slug` and every `users.identity_provider*` column stay untouched.** They are stable identity/lookup keys, not PII — the same distinction `organizations_immutable_identity`'s protected-column list already drew between `slug`/`id`/`created_at` (identity) and `display_name` (not listed, therefore always mutable) before this ADR existed.

**A third narrow role, mirroring the two precedents this codebase already established.** `organization_data_steward` (NOLOGIN, BYPASSRLS) owns `anonymize_organization(uuid)`, a `SECURITY DEFINER` function; `app_runtime` gets `EXECUTE` only, never direct table access to the columns being scrubbed. This is the same shape as `identity_provisioner` (ADR 0005, provisioning) and `integration_token_manager` (ADR 0008, token deletion) — a narrow role for exactly one sensitive operation, not a broadened grant on `app_runtime` itself. Two real implementation lessons from building it, worth recording since they'll recur: (1) `BYPASSRLS` bypasses row-level policies, not the base table-level `GRANT` system — the role still needs ordinary `SELECT`/`UPDATE` grants on every table it touches, and `UPDATE` alone is not sufficient when a `WHERE` clause or correlated subquery reads the table's own columns, which needs `SELECT` too; (2) `BEFORE UPDATE` triggers (like `reject_immutable_column_update`) fire regardless of `BYPASSRLS` — an entirely separate enforcement mechanism from RLS, and `leads_immutable_snapshot`'s original column list (every column, including `contact_name`/`company_name`) had to be narrowed to let this function work at all, which is itself a real instance of the "narrow lifecycle fields may change" path ADR 0003 anticipated rather than a violation of it.

**Deactivation is enforced at sign-in, not just displayed.** `resolve_memberships_for_identity` (the function every sign-in resolves through) now excludes organizations with `deactivated_at is not null`. A deactivated organization's former owner gets exactly the same experience as any other signed-out visitor — never a half-scrubbed session with real membership but anonymized display data.

**A disclosed, known gap: `audit_events.metadata` (jsonb) is not scrubbed.** Connector sync events and billing mutations sometimes log identifying detail (an email address, a customer name) inside this free-form column. Scrubbing arbitrary JSON content safely is a real, separate problem this ADR does not solve — audit metadata retention is flagged here rather than silently ignored.

## Explicitly out of scope

Automatic retention-expiry purging (`audit_events.retain_until`/`source_records.raw_payload_retain_until` exist as columns but nothing reads or acts on them yet — this ADR doesn't change that). A customer-facing UI beyond the two Server Actions this ADR's implementation adds (`/profile`'s export/delete controls). Scrubbing `audit_events.metadata`. Multi-organization-aware anonymization beyond the sole-membership guard already built (real today only in the sense that it's correct code with no real multi-org user to exercise it yet — team invites don't exist). Any automatic Stripe subscription cancellation or connector disconnection as _part of_ `anonymizeOrganization` itself — the persistence function deliberately does neither, leaving both to the calling Server Action, since both are real external API calls this layer shouldn't make silently and both already have real, tested functions elsewhere.

## Consequences

A customer can now get a real answer to both "export my data" and "delete my account," closing the gap three independent audits (README, the market-readiness report, this feature's own originating request) agreed was the largest one open. The narrow-role-plus-`SECURITY-DEFINER`-function pattern is now proven a third time, which is worth treating as the standing answer to "how does a privileged, audited exception to append-only data get built in this codebase" rather than re-deriving it per feature.

**Update (2026-08-21, migration 0055)**: this ADR's own scrub list (paragraph above) went stale the moment `messages` (ADR 0050) and `support_tickets` (ADR 0054) shipped — both hold real customer PII (`messages.counterparty_name`/`counterparty_email`, `support_tickets.requester_name`) that `anonymize_organization` never touched, a real gap, not a hypothetical one: a customer requesting deletion after connecting Gmail or Zendesk would still have that PII sitting in the database afterward. Migration 0055 closes it, extending the same function and the same `organization_data_steward` role rather than a new mechanism — `messages.counterparty_name` → `null`, `messages.counterparty_email` → the same `'[deleted]'`-style placeholder `leads.contact_name`/`invoices.customer_name` already use (that column is `NOT NULL`), `support_tickets.requester_name` → `null`, `support_tickets.assignee_name` → `null` (mirroring `tasks.assignee_name`'s own precedent exactly). Free-text fields (`messages.subject`/`snippet`/`body_preview`, `support_tickets.subject`) stay untouched, the same disclosed-limitation class this ADR already accepts for `audit_events.metadata`. `exportOrganizationData` gained matching `listAllMessages`/`listAllSupportTickets` reads in the same pass, closing the analogous read-side gap (the export's own doc comment claims "every real record," which wasn't true for either entity until now). Any future entity added to the Business Graph should extend `anonymize_organization` and `exportOrganizationData` in the same migration that adds the entity, not as a follow-up gap — recorded here so it isn't missed a third time.
