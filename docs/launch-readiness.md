## Classification key

| Status                         | Meaning                                                                                                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `VERIFIED`                     | Built, and directly confirmed working against a real database/live server/real external endpoint this session or a prior one in this codebase's history — not inferred from code existing.                                                             |
| `IMPLEMENTED_UNVERIFIED`       | Real code exists and typechecks/passes its unit or fixture tests, but has never been exercised against the real thing it depends on (a live third-party API, a real production deploy) — usually because no credential/account exists to test it with. |
| `CONFIGURATION_REQUIRED`       | The code is real and works; a deployment-time setting (env var, dashboard toggle, DNS record) still needs to be set before it's live.                                                                                                                  |
| `EXTERNAL_CREDENTIAL_REQUIRED` | Blocked on an account/credential only a human can obtain (register an OAuth app, get a Stripe live key, buy a domain) — not something further engineering resolves.                                                                                    |
| `BUSINESS_DECISION_REQUIRED`   | Blocked on a decision only the product owner can make (pricing, a support email address, which connectors launch first) — the engineering path is otherwise clear once decided.                                                                        |
| `BLOCKED`                      | Depends on something else in this matrix that isn't `VERIFIED` yet — the dependency is named.                                                                                                                                                          |
| `NOT_IMPLEMENTED`              | No real code exists for this yet.                                                                                                                                                                                                                      |

### Per-connector checklist status (real OAuth connectors only)

Every one of the 14 has: real OAuth 2.0 flow (code-complete,
`authStrategy.configuration: "code-ready"`), real Vault-encrypted token
storage, real initial sync into the Business Graph, real disconnect (with
provider-side revocation for 11 of 14 — Jira and Microsoft have no
revoke endpoint at all per their own provider APIs, a disclosed
limitation not an oversight), and real degradation handling (a failed
sync marks the integration `degraded`, doesn't silently succeed).
Incremental sync exists for 8 of 14 (HubSpot, QuickBooks, Asana, Gmail,
Salesforce, Xero, Jira, Zendesk); Slack/Stripe/Google Calendar/Microsoft
Outlook/Microsoft Calendar/Linear currently only support a fresh full
sync via "Sync Now," not a true incremental cursor. Rate-limit handling
is per-connector and code-real but **has never been tested against a
real rate-limit response from any provider** — `IMPLEMENTED_UNVERIFIED`
across the board, since no live account exists to actually trigger one.
Canonical Business Graph mapping is real and tested via fixtures for
every one of the 14.

**None of the above changes the top-line fact: every connector is
`EXTERNAL_CREDENTIAL_REQUIRED` before it can move from
`IMPLEMENTED_UNVERIFIED` to genuinely `VERIFIED` in production.** The
shortest real path: the product owner registers one real OAuth developer
app per Launch Connector Set connector (six accounts/app-registrations
for Tier 1 alone), enters the resulting client id/secret pairs as
production env vars, and someone connects a real account of each and
confirms a real sync completes — see `LAUNCH-BLOCKERS.md`.
